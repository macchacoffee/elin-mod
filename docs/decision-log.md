# 設計判断ログ

コードだけを見ると「なぜこの形なのか」が分かりにくく、将来また同じ議論になりそうな判断を残す。
一時的な実装詳細ではなく、再検討時に根拠として役立つものだけを書く。

## D001: Prefix / Postfix を Transpiler より無条件に優先しない

### 判断

Prefix / Postfix で自然に変更できる場合はそれらを優先する。
ただし、必要な変更が vanilla メソッド内部の一部分にあり、Prefix / Postfix では vanilla 処理を大量にコピーする必要がある場合、限定的な Transpiler を選ぶ。

### 理由

- vanilla 実装のコピーはゲームアップデート追従時の差分が大きくなりやすい。
- 適切に限定した Transpiler なら「変更したい一部分」だけを差し替えられる。
- Transpiler の壊れやすさは matcher と失敗検出の設計である程度管理できる。

### 再検討条件

- Harmony / ゲーム側により安定した hook point が追加された場合。
- Patch 対象メソッドが頻繁に変更され、Transpiler の維持コストが vanilla コピーより明確に高くなった場合。

---

## D002: Transpiler は誤適用より検出可能な失敗を優先する

### 判断

ゲームアップデート後も何となく matcher が一致するよう過度に緩くせず、想定した IL が変わった場合に確認できる実装を好む。

### 理由

静かに別の instruction を書き換える方が、Patch が明確に失敗するより原因特定が難しいため。

---

## D003: hot path の設計は実測してから変える

### 判断

毎フレーム実行、Reflection 使用、文字列処理などの特徴だけを理由に再設計しない。
呼び出し頻度、実測時間、allocation、変更による複雑性を合わせて判断する。

### 理由

小さな処理を避けるために invalidation や event 管理を複雑化すると、性能改善より correctness / 保守性のコストが大きくなる場合がある。

---

## D004: 相談とコード変更を分ける

### 判断

「どう思う？」「調べて」「レビューして」のような依頼では、明示されない限りコードを変更しない。
実装方針を相談した後、ユーザーが実装を選んだ段階で変更する。

### 理由

設計比較の途中で Codex が先にファイルを書き換えると、検討と実装の境界が崩れ、不要な diff が発生するため。
