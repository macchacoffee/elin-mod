# Elin 内部処理 調査ノート

ここには、複数の Mod で再利用できる Elin 内部処理の注意点を残す。
個別メソッドの実装はゲームアップデートで変わるため、古い記録を現在の真実として無条件に扱わない。

## Harmony バージョン

- この開発環境では Harmony の比較的古いバージョンを使用しており、`PatchCategory` を利用できる前提にしない。
- 新しい Harmony の API を提案する場合は、参照中バージョンで利用可能か確認する。

## ハードコードされた特殊処理

Elin では、一見汎用システムだけで処理されていそうな機能にも、個別条件がハードコードされていることがある。

調査時は以下を意識する。

1. 共通処理だけで結論を出さない。
2. 対象 ID、Feat、Element、Card type などを直接比較している箇所も検索する。
3. 呼び出し元で例外処理されていないか確認する。
4. setter / helper の名前だけでなく、直接 field を変更するコードも探す。

## 死亡状態と HP

- Elin では HP が 0 以下であることと死亡状態を常に同一視できない。
- 「マナの体」のような特殊メカニクスを考慮する必要がある。
- UI や Mod ロジックで死亡を扱う場合は、HP の数値だけではなくゲーム本体が持つ semantic な死亡状態を優先して調査する。

## キャッシュされた戦闘情報

- `GoalCombat` などが保持する一覧は、その場で毎回計算されるとは限らない。
- ability のような一覧を Mod 設定で動的に制限する場合、一覧を作った後に設定だけ変えても既存キャッシュへ反映されない可能性を考える。
- 調査時は「どこで Build されるか」だけでなく、「いつ再 Build されるか」「null / Clear / replace のどれで invalidation されるか」を追う。

## 一見危険な null 処理

vanilla に「この field が null なら初期化関数を呼ぶが、その初期化関数の冒頭では Clear している」など、一見すると null reference に見えるコードが存在する場合がある。

この種のコードはすぐバグ認定せず、以下を確認する。

- 実際にその分岐へ null 状態で到達できるか。
- constructor / Awake / Start / owner 側で事前初期化されていないか。
- decompiler の表現によって初期化が見えにくくなっていないか。
- 呼び出し側が別の invariant を保証していないか。

## この文書へ追記するとき

- 可能なら確認した game version / build を記録する。
- 「確認済み」と「可能性」を分ける。
- 特定 Mod にしか関係しない事項は、その Mod の docs / AGENTS.md へ置く。
